* Problem
StarIntel's rule system is conservatively sound but pays for that safety in duplication, drift, and ceremony: overlapping gate/evidence layers, per-import gate reruns on top of writer-side full-corpus validation, parallel CLI entrypoints, version literals that contradict the declared authority chain, and unenforced permission bits that create false safety. The system's "IQ" — effectiveness per token and per minute — is the target, not its safety margins.

* Verified Facts
- The critique classified 10 findings as load-bearing conservative core (control gate, scripted write path, email/social graph invariants, version authority chain, ID stability, unverified-ledger visibility, RAGE scoping, run-state requirement) and 15 as ceremony/duplication/drift; top-ranked: =top_findings(10, [f08,f04,f03,f15,f11,f07,f06,f02,f19,f09])=.
- The transactional writer and batch importer already validate the complete corpus after writing; a per-import merge-gate rerun re-validates an unchanged corpus (critique f03).
- Two evidence ledgers (skill =verify.py= and global =prolog-verify observe=) record the same argv/exit-status fact in two places (f04); six byte-identical CLI wrappers and three gate entrypoints exist (f07).
- CLI banner/help self-describe a retired version line while the authority chain declares a newer release (f08, contradiction c2); the documented migrator targets the retired line (f09, c6).
- The control-file checker enforces only =enabled= and =state= while the control file declares five permission bits (f02); prose blocks =paused= while the checker requires =running= (f14, c1).
- A multi-subject target query silently emits an empty frontier (f15); a pinned content-addressed dependency path lives in skill law (f11).
- Both modules and loader consult cleanly under swipl 10.0.2; 16 Python tests assert the invariants on synthetic cases (=tests/test_public_starintel_kb.py=, all passing, 2026-09-19).

* Inference
Rules gain IQ when they are (a) general with registries carrying the specifics, (b) enforced by mechanism rather than prose where enforcement is cheaper, (c) gated at boundaries instead of repeated per step, (d) derived from authority instead of hand-copied, and (e) reviewed with a queryable cost/benefit checklist that knows about deletion traps and unenforced safety claims. Encoding the rules as Prolog makes them inspectable: any agent can ask which requirement a task is missing, why a merge is blocked, or which rule is ceremonial, instead of re-reading prose law.

* Contradictions
Inherited from the critique (c1-c8) and carried into the KB as open policy positions: prose-vs-checker state semantics (resolved p13: fail-closed wins), version text vs authority (p05), global 0.9-era prose vs 0.10 reunified line (p05/p09), mandated-but-absent skill (runtime lag; owner action), forgejo-primary vs github issue URLs (operator decision), brave-only vs runtime tools (p14), two-writers-doc vs five-paths-disk (p12). No contradiction inside the public KB itself was found while testing.

* Unresolved Questions
- Should the public KB become a versioned contract (predicates as public API) under the star-kb predicate-compatibility rules, or stay an advisory rulebook?
- What is the registry format for canonical dataset roots (p10) and who checks it?
- Does the evidence ledger (p02) live in the consumer repo or the global policy, and what are its tamper-evidence requirements?
- What vocabulary covers third control-plane states (draining, finishing) beyond running/paused?
- Schema question from f12: an explicit observation-list container for high-cardinality person sets.

These questions gate any promotion from research to design; they are not permission to treat the proposals as approved.
