# Star KB agent instructions

Star KB is the shared durable Prolog knowledge-base corpus for StarIntel.

## Core rule

Do not skip the RAGE gates.

Research -> explicit research approval -> design -> explicit design approval -> implementation -> verification.

A green build is evidence, not approval.

## Current phase

The initial shared-KB research direction is approved. The Prolog corpus/query-server design is pending explicit user approval. Do not create implementation code, populate the corpus, or promote the design into `roam/implement/` until that approval is recorded.

## Source of truth

The Org tree under `roam/` is authoritative for project state:

- `roam/indexes/star-kb.org` — project index and current gate state
- `roam/research/star-kb/` — approved and active research
- `roam/design/star-kb/` — reviewable implementation designs
- `roam/implement/` — only explicitly approved active implementation

Read the active note, its direct links, the project index, relevant source, and relevant tests. Do not dump the whole repository into context for ordinary focused work.

## Knowledge architecture constraints

- Prolog is the canonical fact/rule representation for the initial Star KB corpus.
- Actors should consume shared knowledge through the Prolog query-server contract rather than guessing filesystem paths.
- Facts imported from external sources or generated by models must carry provenance.
- Stored facts and derived conclusions must remain distinguishable.
- Public predicates are contracts; breaking semantic changes require explicit versioning/migration.
- Knowledge is modular. Do not create a monolithic global file.
- Do not let individual actors invent incompatible private versions of shared predicates when the concept belongs in Star KB.
- Learned/neuro-symbolic output is candidate/generated knowledge by default, not trusted canonical truth.
- StarLang may become an authoring/binding layer later, but do not make initial Star KB correctness depend on unfinished StarLang features.

## Durable agent knowledge

When work discovers reusable debugging knowledge, invariants, schema rules, tool behavior, or repository conventions, preserve it in durable Prolog knowledge rather than only in chat text or ephemeral TODOs.

Prefer many focused Prolog files/modules over one growing catch-all file. Runtime observations tied to a specific run or checkout should be stored separately from durable rules and must not silently become canonical domain facts.

## Working rules

- Keep changes bounded to the current approved slice.
- Update the active TODO/state as work progresses.
- Reuse or extend existing tools before creating new ones.
- Add tests for behavior changes.
- Do not claim validation passed unless the exact command was run successfully.
- Do not merge a design into implementation merely because CI is green.
- Keep secrets, generated runtime artifacts, and caches out of Git.

## Validation

Run the repository validation commands before publishing changes:

```sh
python3 scripts/sync.py
python3 scripts/sync.py --check
python3 scripts/validate-docs.py
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

If validation fails, report the exact failure and fix only within the permitted phase/scope.
